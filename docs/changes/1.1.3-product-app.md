# ai-team-sdlc 1.1.3 — Change specification: product-app showcases

Status: implemented in 1.1.3, commits 2f9be96..f48f339

Created by Calin Lupas, Sr Cloud Solution Architect, with AI assistance: the human guides and decides; AI drafts, critiques and executes.

**Scope:** how `ait-product-showcase` and `ait-product-prototype` build and check a prototype, the Simulate kit they share, and the brief `ait-idea` hands them. **A change to three skills and the kit; nothing else moves.**
**Target repo:** `CalinL/ai-team-sdlc` (public). **Base:** release 1.1.2 = tag `1.1.2` (commit `de7b24a`). **New version:** 1.1.3.
All plugin paths are relative to `plugins/ai-team-sdlc/`.

## 0. What this release does, and what it must never break

| # | Change | Behavior after the release |
|---|---|---|
| P1 | **A product app by default:** on the generate path the prototype is a product app (left menu, header, footer, Overview, phone drawer), unless the user asks for a single-page or presentation layout. Showcases use the full shell; quick prototypes a lean one (no search, notifications or user menu), the full shell on request | Changed (intended) for new showcases and prototypes |
| P2 | **Light and dark themes from day one**, with an automated contrast check on every screen in both themes | Changed (intended) |
| P3 | **Overlay rules** in the default acceptance criteria | Changed (intended) |
| P4 | **Simulate:** every beat sets up its own screen; two scenarios (short and full); presentation mode; kit fixes (last-step Next, leftover toasts) | Changed (intended) |
| P5 | **A reusable browser harness** (`ait-product-showcase/assets/check-prototype.py`) with the known pitfalls handled | Additive, optional |
| P6 | **Reviewer brief:** a finance and domain sanity pass; review-loop housekeeping | Changed (intended) |
| P7 | **`ait-idea` briefs:** a calculation ledger, a names check, verified locations, quotes in context, the app-layout expectation | Changed (intended) |

**Guarantees**
1. Only these plugin files change: `skills/ait-product-showcase/` (SKILL.md, `references/simulate.md`, `assets/simulate-kit.html`, new `references/product-app.md`, new `assets/check-prototype.py`), `skills/ait-product-prototype/SKILL.md`, `skills/ait-idea/SKILL.md`, two sentences of `skills/ait-prototype-testing/SKILL.md`, and the version fields. No agent, prompt, other skill, gate catalog or tracking rule changes.
2. The reproduce path is unchanged: it follows the source design, never the app shell.
3. A prototype built from the 1.1.2 kit keeps working: the kit's `CONFIG.steps`, helpers and `window.Simulate` keep their meaning; everything new is optional configuration.
4. The persistent simulated-data disclosure stays visible in every mode, presentation mode included (it lives in the footer).
5. The Playwright MCP stays the default way to verify; the harness is used when Python Playwright is available and it can run, and otherwise its checks are the checklist the MCP run follows; a harness that can't run never blocks a task on its own.
6. All three surfaces keep working: VS Code Local harness, VS Code Copilot harness, Copilot CLI.

## 1. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | The app-shell, theme and overlay rules live in one new reference, `ait-product-showcase/references/product-app.md`; `ait-product-prototype` points to it | One source; keeps both skills short |
| D2 | `ait-product-prototype` builds a **lean shell** by default (left menu, header with breadcrumb and light/dark switch, footer, Overview, phone drawer) at its own fidelity (plain styling is fine), and the **full shell** when the user asks, at high fidelity, or when the flow needs search, notifications or the user menu. A new optional input `shell: lean|full` and a harness flag `--shell lean` carry it | The request covers both skills; three cross-family reviewers found the full shell on every spike fought the skill's "lowest fidelity that validates the flow" identity, so the owner chose a flexible shell |
| D3 | The harness is Python Playwright, optional, run with `python check-prototype.py <file>` (`--tours none` without Simulate, `--layout page` for a requested single page, `--allow-unverified` for text over images checked by eye). It is silent: an init script stubs `speechSynthesis`, because `--mute-audio` alone doesn't silence Web Speech on Windows. The "use only the Playwright MCP; do not invent or install test tooling" rule now also allows this bundled harness | The pitfalls (`text_content`, UTF-8 output) are Python Playwright ones; MCP-only hosts lose nothing |
| D4 | Harness conventions: menu items carry `data-nav` and the active one `aria-current="page"`; `<html data-theme="light|dark">` with a `data-theme-toggle` switch; every overlay opener has `aria-controls` and `aria-expanded`; dialogs have `role="dialog" aria-modal="true"`; the search opener answers Ctrl+K (and ⌘K); scenario menu items carry `data-simulate-run`, demo-only elements `data-demo-only` | A checker needs stable hooks; these are plain ARIA plus a few data attributes |
| D5 | Scenarios: `CONFIG.steps` stays the **full** tour; a new optional `CONFIG.short` returns the short one. Start with `Simulate.start("short"|"full")`, a menu item `data-simulate-run="short|full"`, or Ctrl+Alt+1 / Ctrl+Alt+2 | Backward compatible (Guarantee 3); key codes (`Digit1`, `KeyP`) work on every layout, and Ctrl+Alt avoids Alt+Shift, Windows' keyboard-language switch |
| D6 | Presentation mode: `Simulate.present(on)`, Ctrl+Alt+P, or `?present` in the URL. It hides `[data-simulate]`, `[data-simulate-run]`, `[data-demo-only]`, the progress line, the panel and the spotlight outline. `?cursor` (or `CONFIG.cursor`) shows a visible pointer that glides to each spotlight and click; `?mute` (or M during a tour) turns narration off. Esc exits a tour unless the app consumed it to close an overlay (`preventDefault()`) or the viewer is typing in their own field | One switch for live demos and recordings; one Esc never closes a dialog and kills the demo |
| D7 | The engine calls an optional `CONFIG.closeAll()` when a tour starts and when it exits or finishes, and an optional `CONFIG.dismiss()` (default: hide `.toast.show`) at the start of every beat | "Reset and Simulate exit close everything"; no toast survives into the next beat |
| D8 | Kit shortcuts and the host's own shortcuts are ignored while the viewer types in a field | Overlay rule 5 |
| D9 | A user who stops with one critic READY and the other's review pending gets a recorded user decision, written in `v<N>-changes.md` and the handoff; it stands in for the second READY | Item 8; never silent |
| D10 | The browser tests for the kit and harness run against a fixture app in `tests/showcase/`, built from the kit's own marked blocks (not shipped in the plugin) | Proves the kit and the harness without adding a starter file to the plugin |

## 3. Test plan

### 3.1 Automated (free, `tests/showcase/`)
1. Kit: Next on the last beat ends the tour in under 1s; a toast shown in a beat is gone at the next beat; `closeAll` runs on start and exit.
2. Kit: the short and full scenarios start from a menu item, from the shortcut and from `Simulate.start`, and run the same beats every time.
3. Kit: presentation mode (shortcut, API, `?present`) hides the trigger, menu items, progress, panel, spotlight and `data-demo-only`; navigation and the footer disclosure stay; a tour runs in it with and without the cursor and narration.
4. Kit: shortcuts are ignored while typing.
5. Harness on the fixture app: passes (app shell, every screen in both themes, overlay rules, phone drawer, header on one row, both scenarios, presentation mode, zero console errors).
6. Harness on mutated fixtures fails the matching check: low-contrast ink in dark mode; Esc that doesn't close; two overlays open at once; focus not returned; Tab escaping a dialog.
6b. A lean-shell fixture passes with `--shell lean` and fails `overlays` and `typing` when checked as a full shell.
7. Static checks, recipes and the agent dry run still pass.

### 3.2 Agent probes (model, optional)
8. `ait-product-showcase` on a one-paragraph brief builds an app shell with both themes and two scenarios, and its own harness run passes.

### 3.3 Manual (VS Code Local, VS Code Copilot harness, Copilot CLI)
9. The skills load; `/product-showcase` produces a full-shell product app and `/product-prototype` a lean-shell one by default (full shell when asked), and both a single-page layout when asked.
10. Narration is audible in unmuted Edge in both scenarios, and silent with M or `?mute`.

### 3.4 Review
11. Three reviewers from model families outside the authorship lineage, in parallel, read-only; Critical and Major findings fixed; one confirmation round.

## 4. Release notes
"Showcases and prototypes are now built as product apps by default (menu, header, light and dark themes, footer, Overview; showcases add search, notifications and a user menu, which quick prototypes add on request), with overlay and contrast checks in the gate and a reusable browser harness. Simulate gains a one-minute and a full scenario, a presentation mode for live demos and recordings, and two kit fixes. Reviewers recompute every number. `ait-idea` briefs carry a calculation ledger and a names and locations check."
