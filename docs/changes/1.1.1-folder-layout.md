## 0. What this release does, and what it must never break

| # | Change | Behavior after the release |
|---|---|---|
| L1 | **Spec-driven layout:** requirements, specs, decisions, results, approvals and release records are committed in their own folders; `docs/` is documentation only; **`.copilot-tracking/` holds agent state only, never an artifact** (§2.5) | **Changed (intended)** for runs and phase skills started on 1.1.1 (§2) |
| L2 | **New skill `ait-artifact-layout`:** the single source for "which artifact goes where, and who writes it" | Additive |
| L3 | **Contract-mode path check, hardened:** a task that changes the brief, the requirements, an acceptance receipt or `.github/ai-sdlc.yml` fails, listed or not, tracked or gitignored | Contract mode only |
| L4 | **Credits and licensing:** README credit line, root `NOTICE`, one-line header comment on original files; `skills/NOTICE.md` license sentence corrected (O1) | No behavior change |

**Guarantees**

1. **The team never relocates an existing work product to adopt this layout.** New paths apply to new artifacts. Normal delivery work is unaffected (code refactoring, the Scribe moving processed inbox files).
2. **Runs started on 1.1.0 resume with their 1.1.0 output locations** (§2.4). Their records move to committed homes (O2 applies to all runs): approvals are carried over once to `delivery/approvals.md`, and new decisions go to the decision log. An earlier sign-off stays valid only when a commit SHA proves the approved content is unchanged; otherwise the humans sign off again.
3. **A 1.1.0 `.github/ai-sdlc.yml` still validates, and every key it sets is honored.** One intended difference for **new** runs: keys it omits (`paths.stories`, `paths.specs`, `paths.results`, `decisions`, and `paths.prototype` with `ui-spec`) now default to committed folders instead of the tracking store (§5.1).
4. **Lifecycle, gates, three-approver sign-off, reviewer independence and the contract schema are unchanged**, apart from the `{feature}` placeholder, the `paths.prototype` default (§5) and the L3 hardening. The safety floors keep their strength; O2 (§6) changes only **where** the sign-off record lives and states that writing the approval and release **records** is not a change to the approved release.
5. **All three surfaces keep working:** VS Code Local harness, VS Code Copilot harness, Copilot CLI.

## 1. Why

- **The tracking store is used as an artifact store.** `ait-conventions` calls `.copilot-tracking/` "runtime state … git-ignored", yet in 1.1.0 the PRD, the specs and the ADRs exist only inside `inbox/` handoffs and `decisions.md` (`ait-tech-specs` step 8; `ait-conventions` › Tracking store), the three-approver sign-off record lives only in `decisions.md` (floor 2), and the release plan and deploy evidence only in `ait-devops`'s inbox handoff. Delete the folder, or clone the repo elsewhere, and the specification and the approval evidence are gone.
- **`docs/` is a catch-all.** The prototype, showcase, research, change notes, extras and evidence go to `docs/<product>-*` (§2.4 lists every one). The contract-mode example puts the brief, stories, specs, prototype, conformance and results under `docs/delivery/`.
- **Leading spec-driven tools separate documentation from specifications:**
  - GitHub Spec Kit commits one folder per feature, `specs/<###-feature>/`, holding `spec.md`, `plan.md` and `tasks.md` (https://github.com/github/spec-kit);
  - Kiro commits `.kiro/specs/<feature>/` holding `requirements.md`, `design.md` and `tasks.md` (https://kiro.dev/docs/specs/);
  - decision records live in their own numbered log; adr-tools defaults to `doc/adr/` and makes the folder configurable (https://github.com/npryce/adr-tools).

**Principle:** `docs/` is documentation (guides, how-tos, runbooks, design rationale). Requirements, specifications, decisions, approvals and delivery records are work products, each with a committed home. `.copilot-tracking/` is the agents' local state: it may summarize and link an artifact, never hold one (§2.5).

## 2. The layout (L1)

### 2.1 Default tree

```
specs/                                    committed: the spec-driven tree
  README.md                               written once, never overwritten (template in §3)
  prd.md                                  the PRD: requirement IDs, acceptance criteria ("the what")
  design/                                 journeys, UX flows, tokens (only when the design stage runs)
  ui/                                     the prototype: prototype-v<N>.html, notes.md, v<N>-evidence/
    ACCEPTED.md                           contract mode: the human's prototype acceptance (never the team)
  features/<NNN-slug>/                    one folder per feature: an epic from the PRD, or part of one
    stories.md                            the feature's user stories, each citing requirement IDs
    <NNN-slug>.md                         the implementation spec, named after its folder ("the how")
    tasks.md                              the committed task plan (static; no status)
architecture/
  adr/NNN-kebab-title.md                  decision records (any specialist proposes; humans accept)
delivery/
  brief.md                                contract mode: the run's brief (owned outside this team)
  conformance/<spec>.md                   contract mode: conformance receipts (owned outside this team)
  results/                                QA, review, security and evaluation results
    acceptance-<version>.md               contract mode: the human's release acceptance (never the team)
  approvals.md                            append-only: the sign-off record, gate confirmations, waivers (O2: the record)
  release/                                release plan, rollback plan, deploy evidence
showcase/<company>/ | <use-case>/            idea material by company; one showcase per use case
docs/                                     documentation only
.copilot-tracking/<run-id>/               gitignored agent state only (§2.5): state.json, plan.md, inbox/, baselines
```

In `showcase/`, `<company>/` holds one `ait-idea` run (its use cases share one research dossier) and `<use-case>/` holds one showcase: `<use-case>` is a kebab-case slug of the business case, prefixed with the company when one is known (`acme-expense-approvals`; `expense-approvals` without a company), so a showcase never needs a company name. (Owner decision after implementation review: the showcase folder is keyed by the use case, not the company.)

Code, tests and infrastructure stay in the **host's existing layout**. The one existing code default stays as is: `ait-wireframe-to-frontend` reproduces into the caller's folder, else the repo's frontend convention, else `apps/frontend/`.

**Why `architecture/adr/` and not a root `decisions/`:** a repo whose architecture is owned by someone else (the contract-mode case) keeps decisions with its architecture. One default for both modes means a team that starts in default mode and later adopts contract mode doesn't move its log. `decisions.dir` still moves it anywhere.

### 2.2 Features, stories and tasks

1. **One slicing owner.** The product owner slices the PRD (default mode) or `contract.requirements` (contract mode) into feature folders: each folder is one epic or part of one, numbered `NNN-slug` in creation order. Requirement IDs inside the files may map many-to-many. Nobody else creates or re-slices feature folders; the orchestrator's decomposition reads them.
2. **Stories live in their feature.** Spec Kit keeps user stories in each feature's `spec.md`, Kiro in each feature's `requirements.md`. A product-wide stories file grows without bound, conflicts on merge and loses the link between a story, its spec and its tasks. Story IDs are `S<NNN>-<n>` (feature number, story number), each with acceptance criteria and the requirement IDs it covers.
3. **The spec is named after its folder.** `features/001-checkout/001-checkout.md`. `{spec}` in `external_gates` is that name without extension, so every conformance receipt is unique. Never a generic `spec.md`. `spec-conformance` binds to the **file digest of that one file**, so edits to `stories.md` or `tasks.md` never make it stale.
4. **`tasks.md` is a static plan.** The architect writes it with the spec, one table row per task, with the existing task-template columns minus `gateResults` and `status`, plus `ref` and `story`: `| ref | story | title | owner | phase | deps | acceptance | requiredGates |`. `ref` is `<NNN>-<n>` (feature number, task number) and `deps` cite refs. At decomposition the orchestrator imports each row into `state.json` under the **canonical runtime id** (`T-001`, `T-002`, … as today), storing `ref`, `feature` and `story` as extra task fields (A5), and rewrites each task's `deps` from refs to those runtime ids. From then on `state.json` is canonical and status lives only there and in its projections, so parallel tasks and sign-off never touch the committed plan. A change to the plan is a new architect task before sign-off, which rewrites the file and re-imports it (matching by `ref`).

### 2.3 Rules

1. **Decision records are committed.** Any specialist may add a **new** Proposed record in the decision log; the architect owns architecture decisions; only a human sets Accepted. A small implementation choice that doesn't merit a record goes in a `## Decisions` section of the feature's spec. There is no `decisions.md` in a 1.1.1 run (§2.5): the decision log, `delivery/approvals.md` and the specs' `## Decisions` sections are the record.
2. **Approvals are committed (O2).** The sign-off record (three approvers, verbatim quotes or references, the release candidate, timestamp), every gate confirmation and every waiver are appended to `delivery/approvals.md` **when they happen**: the orchestrator records sign-off; the Scribe records gate confirmations and waivers. Gate, sign-off, deploy and resume checks read `delivery/approvals.md`, in every run on 1.1.1.
3. **Results and release records are committed:** results in `delivery/results/`; the release plan, rollback plan and deploy evidence in `delivery/release/`, written by `ait-devops` as it works.
4. **Human-only files are never written by the team:** `specs/ui/ACCEPTED.md`, `delivery/conformance/*`, `delivery/results/acceptance-*`, `delivery/brief.md` and the requirements file (contract mode).
5. **No row fits:** don't write the artifact anywhere, not even the tracking store, and never default to `docs/`. Return its content only in the conversational reply and ask the human where it goes. In a run, the inbox handoff records only the routing blocker (what the artifact is, and that it needs a destination); that task stays `blocked` until the human names a destination and the artifact is committed there. Other ready tasks continue.
6. **The release candidate and the records (O2).** As soon as Build and Test are green, the orchestrator records the release candidate's commit SHA in `state.json.signoff.artifact` (both modes; contract mode already does, `ait-contract-mode` §13). "Any change after approval voids sign-off" is checked against that SHA. **The only changes that don't void it are new records:** an append to `delivery/approvals.md` (its content at the candidate is an unchanged prefix), a new file under `delivery/release/` that didn't exist at the candidate, and a new human receipt matching an `external_gates[].file` pattern (contract mode; it keeps its own digest and confirmation checks and its write protection, §5.3). Editing or deleting an earlier record, or any other change, voids sign-off as today. The records are committed after the release candidate, never inside it.
7. **Only the orchestrator and the Scribe write `delivery/approvals.md`.** A dispatched specialist task never does; in contract mode the path check enforces it (§5.3).
8. **The file names, the ID formats and the three acceptance gates are this team's convention;** the tools in §1 inform only the folder-per-feature shape and the separate decision log.

### 2.4 Resolution order and backward compatibility

For each artifact, the first rule that gives a path wins. Rule 4 applies **only to a resumed run**; a new run, or a phase skill run on its own, skips it and then records what it resolved in `state.json.layout.paths` (when there is a run):

| # | Source | Notes |
|---|---|---|
| 1 | An output folder given explicitly on the invocation | Existing skills accept one (prototype, showcase, idea, wireframe) |
| 2 | `contract.paths` / `contract.decisions.dir` | Contract mode |
| 3 | The host repo's rules (`AGENTS.md`, `.github/copilot-instructions.md`) | G1 |
| 4 | A resumed run's recorded paths | `state.json.layout.paths`; a resumed run whose `state.json` has no `layout` (started on 1.1.0) uses the 1.1.0 table below |
| 5 | An existing version series | Only if 1–3 give nothing: the next prototype or showcase version is written beside the existing ones, and the result says so |
| 6 | The §2.1 defaults | |

**1.1.0 locations** (used by rule 4 for a resumed 1.1.0 run, and by rule 5 to find a version series):

| Artifact | 1.1.0 location |
|---|---|
| PRD, specs, stories, ADRs, results, release plan, deploy evidence | Inside the specialists' inbox handoffs (`.copilot-tracking/<run-id>/inbox/<ts>-<agent>-<task-id>.md`), consolidated by the Scribe into `decisions.md` and `changes.md`; contract mode: the `.github/ai-sdlc.yml` paths, unset `paths.*` in the handoffs, unset `decisions` in `decisions.md` |
| Sign-off record, gate confirmations, waivers | `.copilot-tracking/<run-id>/decisions.md` |
| Prototype | `docs/<product>-prototype-v<N>.html`, `docs/<product>-prototype-notes.md`, `docs/<product>-prototype-v<N>-evidence/` |
| Showcase | `docs/<product>-v<N>.html` (or `docs/<product>-v<N>/index.html`), `docs/<product>-research.md`, `docs/<product>-v<N>-changes.md`, `docs/<product>-v<N>-evidence/`, extras `docs/<product>-<extra>.md` (and `-business-case.html`) |
| Idea | `docs/<company>-research.md`, `docs/<company>-use-case-<NN>-<idea>.html`, `docs/<company>-use-case-<NN>-<idea>-brief.md` |

A run that starts on 1.1.1 records its resolved destinations in `state.json.layout = { "version": "1.1.1", "paths": { … } }`, so a resume never re-derives them.

A resumed 1.1.0 run keeps its 1.1.0 **output locations** (above). Its **approval record moves** (O2 applies to all runs): on the first resume under 1.1.1, the orchestrator appends the run's existing sign-off record, gate confirmations and waivers from `decisions.md` to `delivery/approvals.md`, verbatim and marked "carried over from `.copilot-tracking/<run-id>/decisions.md`", commits that file, and from then on reads and writes only `delivery/approvals.md`. Carrying the records over is an append of new records (§2.3 rule 6). A sign-off given before the resume stays valid **only if** the run's `signoff.artifact` is a commit SHA and the working tree still matches it apart from new records; otherwise (a 1.1.0 default-mode run may have recorded an artifact name or version) the orchestrator resets `signoff` to `pending` and asks for a fresh three-approver sign-off. The run's existing `changes.md`, `decisions.md` and `tasks.md` are left in place, read-only, and no longer written: from the resume on, the run's new decisions go to the committed decision log (`decisions.dir`, or `architecture/adr/` when unset), its approvals to `delivery/approvals.md`, and its file history to Git and `state.json`.

### 2.5 What `.copilot-tracking/` may hold

**Reduced to four kinds of agent state.** A run on 1.1.1 creates and writes only:

| Kept | Why |
|---|---|
| `state.json` | Canonical run state: tasks, status, gate results, lineage, `layout`, `signoff` |
| `plan.md` | The one human-readable progress view, a projection of `state.json` |
| `inbox/` (and `inbox/processed/`) | Handoffs: messages that summarize an artifact and link its committed path |
| Path-check baselines | Contract mode's before/after hashes |

| No longer created or written | Replaced by |
|---|---|
| `decisions.md` | The decision log (`architecture/adr/`), `delivery/approvals.md`, the specs' `## Decisions` sections |
| `changes.md` | Git history, plus each task's `files` in `state.json` (authorship lineage) |
| `tasks.md` (the projection) | The committed `specs/features/<NNN-slug>/tasks.md` (the plan) plus `state.json` and `plan.md` (status) |

The tracking templates for these three files stay in the plugin for runs started earlier, unused by new runs. **No artifact's only copy lives there**: deleting the folder, or cloning the repo elsewhere, must lose no requirement, spec, decision, result, approval or release record. **"Committed" means:** the artifact is written to a tracked path and included in a Git commit of that path. Commits follow the host's rules (G1): the orchestrator commits the batch's artifacts after each batch, unless the host leaves commits to people, in which case it asks. A specialist writes its artifact before the handoff that links it. Before recording the release candidate, the orchestrator makes sure every artifact of the run is in a commit. The approval and release records are committed after the candidate, in commits that touch only those paths.

### 5.3 Path check, hardened (L3)

**Baseline (before each dispatch), added:** the SHA-256 (or "absent") of `contract.brief`, `contract.requirements`, `.github/ai-sdlc.yml`, `delivery/approvals.md`, and every existing file matching an `external_gates[].file` pattern (`{spec}` and `{version}` read as `*`), **whether or not Git tracks or ignores them**.

**After the task, added candidates:** those inputs whose hash changed, appeared or disappeared, and any new file matching a gate pattern (found on disk, not only through Git).

**Per changed path, in order** (the first match decides):

1. under `frozen` → **fail**;
2. `contract.brief`, `contract.requirements`, `.github/ai-sdlc.yml`, `delivery/approvals.md`, or a file matching an `external_gates[].file` pattern → **fail** (no exception, even inside `decisions.dir`);
3. a **new** file in `decisions.dir` whose status is `proposed_status` → allowed;
4. under `protected` or in `decisions.dir` → **fail**;
5. anything else → allowed.

**Then, once per task, even when no path changed:** if `contract.path_check` is set, run it; a non-zero exit → **fail**. `path-check` passes only when no path fails and that command (if any) exits 0.

In 1.1.0, step 2 was a "never write" instruction only; a task could change those files and pass.
