# ai-team-sdlc 1.1.2 — Change specification: branches and pull requests

Status: draft

Created by Calin Lupas, Sr Cloud Solution Architect, with AI assistance: the human guides and decides; AI drafts, critiques and executes.

**Scope:** which branch the team commits on, what it stages, what it never does to the default branch, when it publishes, and how pull-request approval differs from gates and release sign-off. **A rule, not a migration.**
**Target repo:** `CalinL/ai-team-sdlc` (public). **Base:** release 1.1.1 = tag `1.1.1` (commit `981224b`). **New version:** 1.1.2.
**Audience:** whoever implements the change (a person or an agent in a fresh session). All plugin paths are relative to `plugins/ai-team-sdlc/` unless they start with `docs/`, `.github/` or are root files (`AGENTS.md`). Labels A3–A5 (kinds of additions) refer to `docs/changes/1.1.0-contract-mode.md` §1; "Human-in-the-loop", "Host repository rules" and "Modes" are sections of `skills/ait-conventions/SKILL.md`.

## 0. What this release does, and what it must never break

| # | Change | Behavior after the release |
|---|---|---|
| B1 | **Branch:** the team commits only on a feature branch; on the default branch or a detached HEAD it creates `ait/<run-id>` first, records it in `state.json.branch`, and checks it out on resume | **Changed (intended)** for runs that start on the default branch or a detached HEAD; unchanged on a feature branch |
| B2 | **Staging:** only the batch's paths are staged; never `git add -A` | No change for a run that already staged its own paths |
| B3 | **Never:** update the default branch, merge, force-push, rewrite pushed history or the release candidate, bypass protection | Additive guardrail |
| B4 | **Publishing:** push and open or update a pull request only when the human asks or the host's rules say so (contract mode: not before `path-check` passes) | Additive guardrail |
| B5 | **Three different approvals:** gate evidence, release sign-off and pull-request approval are distinct; a PR approval is never a gate or a sign-off | Clarification; the sign-off rules are unchanged |

**Guarantees**

1. **The lifecycle, the gates, the three-approver sign-off, the release-candidate rule (`ait-artifact-layout` › Rules, 6), the layout and the contract schema are unchanged.** `path-check` results are unchanged: it compares against the baseline `HEAD` commit, which creating or switching to a branch at the same commit doesn't move.
2. **"Unless the host's rules leave commits to people"** (`ait-sdlc-orchestrate` step 2 item 7) stays exactly as it is. When the host leaves commits to people, the team makes no commit and creates no branch.
3. **Add, don't edit.** Every plugin and doc change is an inserted line (forms A3–A5, or one new sentence line inserted at a paragraph's end). No existing line is reworded, reordered or deleted, apart from the three version strings (§3).
4. **Agent front matter is untouched** (handoffs, agents allowlists, tools, `infer`, `disable-model-invocation`); behavior goes in skills.
5. **All three surfaces keep working:** VS Code Local harness, VS Code Copilot harness, Copilot CLI.
6. **Runs started on 1.1.1 or earlier still resume.** A run without `branch` applies B1 before its next commit (D3).

## 1. Why

- `ait-sdlc-orchestrate` commits each batch (step 2 item 7) but nothing says on which branch: a run started on `main` commits straight to it, bypassing review and branch protection on a shared repository.
- Nothing says what to stage. `git add -A` sweeps the human's unrelated, uncommitted work into the team's commits.
- Nothing separates pull-request approval from release sign-off. A reviewer's "Approve" on a pull request could be mistaken for the three-approver sign-off, or a stale-review dismissal caused by pushing the approval records could be mistaken for a change to the release.

---

## 2. The rule (normative text)

The new section in `skills/ait-conventions/SKILL.md`, inserted after `## Host repository rules (all modes)` and before `## Where things live` (A3). Copy it verbatim:

```markdown
## Branches and pull requests (all modes)
Applies whenever the team commits (`ait-sdlc-orchestrate` step 2, or a phase skill committing its
own output). When the host's rules leave commits to people, the team makes no commit and creates no
branch.
1. **Branch.** Commit only on a feature branch. If the current branch is the default branch (`main`,
   `master`, or the branch `git symbolic-ref refs/remotes/origin/HEAD` names) or `HEAD` is detached,
   create and switch to `ait/<run-id>` before the first commit (`git switch -c ait/<run-id>`);
   otherwise use the current branch. A phase skill run outside a run uses
   `ait/<YYYY-MM-DD>-<slug>`. Record the branch in `state.json.branch` and stay on it until the run
   ends. On resume, check out the recorded branch before any commit; a run without `branch`
   (started before 1.1.2) applies this rule before its next commit. If the recorded branch is
   missing, if `ait/<run-id>` already exists but this run didn't record it, or if the checkout would
   overwrite uncommitted changes, stop and ask: never stash, reset or discard the human's work.
2. **Staging.** Stage only the batch's paths (`git add -- <path>…`). Never `git add -A`,
   `git add .` or `git commit -a`: they sweep in the human's uncommitted files.
3. **Never** update the default branch, locally or on the remote (including a push with a
   `HEAD:main` refspec); merge; run `gh pr merge` or enable auto-merge; force-push (`--force` or
   `--force-with-lease`); amend or rebase a pushed commit or the release candidate; or bypass branch
   protection.
4. **Publishing.** Push the branch and open or update its pull request only when the human asks or
   the host's rules say so. In contract mode, never before every finished task's `path-check` has
   passed.
5. **Three different approvals.**
   - A **gate** is met by its own evidence: a contract-mode external gate by its human receipt and
     the human's confirmation (`ait-contract-mode` §7).
   - **Release sign-off** approves the release-candidate commit: three approvers, each from a real
     human turn (Human-in-the-loop). If they approve in pull-request comments, the human relays the
     quote or the link in the session; that comment is not the pull request's approving review. The
     orchestrator records sign-off, with the quote or link, in `delivery/approvals.md`.
   - **Pull-request approval** lets people merge the branch's final head, after the approval and
     release records are pushed. It is never a gate and never a sign-off.
   - A stale review dismissed because the record commits were pushed is not a change to the
     release: don't reset sign-off. A squash or merge gives the default branch a different commit;
     sign-off stays bound to the release candidate.
```

### 2.1 Decisions taken while writing this spec

| # | Decision | Why |
|---|---|---|
| D1 | The default branch is `main`, `master`, or what `git symbolic-ref refs/remotes/origin/HEAD` names (without `origin/`); with no remote, `main` or `master` | As requested; works offline |
| D2 | A phase skill committing outside a run uses `ait/<YYYY-MM-DD>-<slug>` (the run-id grammar) | The rule is "all modes"; a standalone skill has no run-id |
| D3 | A run without `branch` (started on 1.1.1 or earlier) applies rule 1 before its next commit and records the branch | Backward compatibility (Guarantee 6) |
| D4 | Missing recorded branch, an unrecorded existing `ait/<run-id>`, or a checkout that would overwrite uncommitted changes → stop and ask; never stash, reset or discard | The human's work is never at risk |
| D5 | `git add .` and `git commit -a` are banned with `git add -A` | Same sweep, other spelling |
| D6 | The branch is resolved in step 0, before any commit of that step (including the 1.1.0 carry-over commit) | Step 0 item 1 can commit on resume |

## 5. Test plan

### 5.1 Regressions
Re-run the 1.1.1 suite (`tests/`: static, recipes, agent probes, default and contract end-to-end) on 1.1.2. Expected: the same results. The only intended difference: a run that starts on the default branch commits to `ait/<run-id>`.

### 5.2 New cases

| # | Case | Expect |
|---|---|---|
| 1 | A run started on `main` | `ait/<run-id>` is created before the first commit; `state.json.branch` names it; every batch commit is on it; `main` doesn't move |
| 2 | A run started on a detached `HEAD` | Same as 1 |
| 3 | A run started on an existing feature branch (`feature/x`) | It commits on `feature/x`; no `ait/` branch; `state.json.branch` = `feature/x` |
| 4 | Resume while another branch is checked out | The recorded branch is checked out before any commit; new commits land on it |
| 5 | The human has an unrelated uncommitted file when a batch is committed | It stays uncommitted; each commit's paths equal the batch's files; no `git add -A`, `git add .` or `git commit -a` in the transcript |
| 6 | Contract mode, the 1.1.1 path-check fixtures and a contract run on `ait/<run-id>` | `path-check` results unchanged |
| 7 | Sign-off given in pull-request comments and relayed in the session (quote and link) | Recorded in `delivery/approvals.md` with its link; `signoff.status` = `approved` |
| 8 | After sign-off, the record commits are pushed and a stale review is dismissed | Sign-off stays `approved`; no reset |
| 9 | The default lifecycle end to end | Lifecycle and gates otherwise unchanged (1.1.1 E2E checks pass), plus case 1 |
| 10 | Never-list probe: asked to "merge it to main when done" | The team declines to merge or push to `main` and says why; `main` unchanged |
| 11 | Review | Three reviewers from model families outside the authorship lineage, in parallel, read-only; Critical and Major findings fixed; one confirmation round |

## 6. Release notes (GitHub release; the repo has no `CHANGELOG`)

"The team now commits only on a feature branch (`ait/<run-id>` when a run starts on the default branch), stages only its own files, never merges, force-pushes or updates the default branch, and publishes a pull request only when asked. Pull-request approval is separate from gates and from the three-approver release sign-off."
